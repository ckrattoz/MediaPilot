# How to contribute

Thanks for wanting to improve MediaPilot. This document explains how work is
done in the repository.

## Before you start

- **Phases are authorized.** The project is organized in phases, and each one
  needs the go-ahead from the repository owner before the next one starts. If
  the proposal includes architecture changes, the decision records
  ([ADR](docs/architecture/adr/)) are the place where the reasoning is written
  down.
- **The original repository is not touched.** `MultimediaHotkeys` (AutoHotkey
  v2) is the functional reference: it is read and cited, but not modified. All
  the new code lives in `MediaPilot`.
- **Versioning is administered by the repository owner.** Branches, commit
  messages, tags and releases follow
  [`docs/development/git-workflow.md`](docs/development/git-workflow.md).
  Contributors open a branch and a pull request instead of pushing to `main`.

## Environment

1. Install the .NET 10 SDK (`global.json` pins the minimum version).
2. Install the Visual Studio 2022 Build Tools with the *.NET desktop
   development* workload and the Windows SDK 10.0.26100 or later.
3. Restore the dependencies:

   ```powershell
   dotnet restore MediaPilot.slnx
   ```

`NuGet.config` is at the repository level on purpose: it pins `nuget.org` as
the only source so that the build is reproducible on any machine.

## Workflow

```powershell
./build/build.ps1                              # build + tests
dotnet test MediaPilot.slnx -c Release         # tests only
dotnet run --project src/MediaPilot.App/MediaPilot.App.csproj
```

Before opening a proposal:

```powershell
dotnet build MediaPilot.slnx -c Release   # 0 warnings, 0 errors
dotnet test  MediaPilot.slnx -c Release   # every test in green
```

The repository builds with `TreatWarningsAsErrors` and the .NET analyzers in
`Recommended` mode. A warning **is** an error: changes that leave warnings
behind are not pushed.

## Code style

- **English** for type, method and identifier names; code comments and XML
  documentation are also in English. The user interface text stays in Spanish
  and lives in the resource files.
- **English** for the public APIs exported in the assembly and for the
  identifiers auto-generated by the compiler.
- XML documentation (`///`) on every public member: `GenerateDocumentationFile`
  is enabled and the warnings are treated as errors.
- Descriptive names without cryptic abbreviations. `HotkeyBinding` is
  preferable to `HKB`.
- The layers follow a strict dependency rule:
  - `Core` knows neither Windows nor WPF.
  - `Configuration` does not know WPF.
  - `Localization` knows neither Windows nor WPF.
  - `Platform` speaks Win32, not WPF.
  - `UI` does not call Win32 directly.
  - Only `App` (and `CompositionRoot`) knows the concrete implementations.

## User interface text

- Every user-facing string lives in
  `src/MediaPilot.Localization/Resources/Strings.resx` (Spanish) or in a
  satellite file `Strings.<culture>.resx`. Text is never hardcoded in the
  sources or in the XAML.
- In XAML the string is resolved with the `loc` markup extension:
  `{loc:Localize Settings_Heading}`.
- The interface uses the **simple hyphen**, never the em dash or the en dash.
- The complete procedure, including how to add a language, is in
  [`docs/development/internationalization.md`](docs/development/internationalization.md).

After adding or renaming a key, run the validation script:

```powershell
./build/i18n.ps1 -Check
```

## Tests

- All logic with observable behavior comes with a test.
- Test names are `Method_Scenario` in English: `DefaultHotkeys.All` contains
  exactly seven mappings.
- `MediaPilot.Core.Tests` does not depend on Windows;
  `MediaPilot.Platform.Tests` does, because the platform tests touch the real
  API.
- `Thread.Sleep` is not used for synchronization: it is preferred to wait for a
  condition with a time limit.

## Commits

The format is [Conventional Commits](https://www.conventionalcommits.org/):
`<type>(<scope>): <subject>`. The subject is in the imperative mood, in
English, and without a trailing period.

```
feat(hotkeys): add SMTC track title integration
fix(tray): reflect the disabled state in the tray icon
docs: explain why waveOutGetVolume was discarded
```

Refactors and behavior changes are not mixed in the same commit: if the change
alters what the user perceives, it goes in its own commit and is mentioned in
the [CHANGELOG](CHANGELOG.md).

The full workflow, with the branch layout, the tagging rules and the release
process, is in
[`docs/development/git-workflow.md`](docs/development/git-workflow.md).

## Documentation

- Every technical decision with discarded alternatives is recorded as an ADR
  in `docs/architecture/adr/`.
- `CHANGELOG.md` is updated with every observable change.
- `README.md` describes the real state of the project; if a feature is planned
  but not implemented, it says so explicitly.
- The documentation is written in American English. Only the user interface is
  in Spanish.
